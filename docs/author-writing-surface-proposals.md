# A calmer writing surface

This records the proposal and subsequent implementation status for the writing-surface cycle dated 28 August 2026. The stable palette and deliberate task-pane design was approved for implementation; the original reasoning and acceptance requirements are retained below. The resumed review combines specialist source review, automated regressions, and actual Chromium layout and interaction checks on the designated review site. Device input, assistive technology, native-picker operation, saved PDF, and physical printing still require separate qualification. Approval of this bounded implementation does not imply those checks passed.

The team includes a **Golden Krishna-inspired review lens**: a role that questions unnecessary interface work and asks how quickly the musician can do the next intended thing. Golden Krishna did not participate personally, and this document does not imply his endorsement or quote him.

## Implementation status — 28 August 2026

Specialist reviews closed their findings after bounded fixes and regressions. Scripted input, controlled layout fixtures, actual browser interaction, and unperformed device/output checks are identified separately.

- **Stable writing intent:** Write notes and Select remain visible in fixed slots. Write notes resumes saved destination C even when B is selected; pressing the active Write notes control only focuses the score. Start writing here remains the deliberate way to establish another point. Read/Pages suspend and restore the prior intent without editing music. Retained task A, selection B and writing point C keep independent identities and guards.
- **Compact entry:** the current-kind Options menu holds the recipe and less common settings; a separate native Value popover holds duration and dots. Insert here remains the secondary exact-entry route. Prepared note/rest handles and Done replace an always-visible drag action. Browser measurements confirm a 48px normal strip with controls at least 44px square at 390 × 660 and 390 × 360 with default text. - **Blank work and rests:** only the blank pitched, rhythm and three-roads starters now begin with empty incomplete voices. Composed studies and Add measure retain authored/explicit rests. Staff click and prepared-handle drop accept ordinary written rests on all three staff modes, using explicit duration, dots, voice and musical boundaries. They do not place full-measure rests, infer pitch from height, relocate an existing rest or invent intervening silence.
- **Keyboard continuity:** in Write notes, N chooses the staff's note tool and R an ordinary rest without writing; Left/Right moves the saved writing point without replacing selection or editing music. Escape cancels a chooser or gesture but does not otherwise leave writing. Enter and the supported A–G route remain explicit musical entry.
- **Complete selected pitch:** the compact Pitch chooser exposes letter, octave and all nine absolute alterations for an eligible untied single note. - **Notation and tools:** the writing frame is measured independently of More. A task uses spare width beside that frame or a deliberate sheet with Return to score, preserving its musical anchor, drafts and scroll. Opening More does not shrink ink, change system breaks, or navigate to an earlier selected instruction. Keyboard help is a closed inline disclosure. Native popovers remain the small-menu mechanism; the optional note-relative toolbar remains off by default.
- **Feedback:** the header owns a compact one-line global summary; full details remain in Review and the accessible label. Active pointer feedback begins with pitch or rest value, ahead of an earlier refusal or held draft; recovery and pending Source remain higher priority. Writing guidance disappears when writing is parked. Routine notation notices live in Review so completing a bar no longer moves the staff. Fatal rendering errors remain visible. A chooser keeps its own local error announcement while open. Recovery failures persist through routine status and navigation, with Review → Download project available; requesting a download does not confirm a file was saved or dismiss the local-recovery failure.
- **Continuation:** eligible Add + insert shows the new bar in its existing button and the full destination in the header and accessible label. The caption fits inside the unchanged compact control. Final endings retain a separate Continue piece decision; nothing creates a bar merely because the previous one became full.
- **Road direction:** a dedicated next-note Direction chooser beside Value exposes Higher, Same and Lower without reopening general Options. Other note options remains reachable from it. Direction changes only prepare the recipe; Insert here/Enter still writes the road note, and there is no road-note pointer entry.

The dedicated entry Direction route has completed its bounded automated and composer review; existing selected-road direction editing remains supported. The integration tests include separate real-Author 32-pointer and 32-keyboard note journeys, the mixed 30-event phrase, exact Undo restoration, source-invalidated writing destinations, delayed task-sheet return, and persistent recovery warnings. Added regressions prove that changed and unchanged pitch drops select their actual note without moving the writer, replacing its recipe, or retargeting a dirty Properties draft. Rendering and browser boundaries are controlled in these tests. The resumed browser review adds actual layout and selected interaction evidence without qualifying hardware input or printed output.

## Original design decision and requirements

The recommendation is to make the score the main work surface, with one compact, stable music palette and one deliberately opened task pane. The current separation of writing destination, selected music, and retained drafts should remain. The proposal changes how those responsibilities are presented, rather than asking the musician to manage several forms before writing a note.

At proposal review, the app already provided direct single-note entry, independent selection and writing bookmarks, a shared bottom dock, Properties plus three general-tool tabs, native popovers, and guarded musical commands. The visible entry-drag handle was inside the entry toolbar, hidden in Select; controller-level admission tests did not establish a visible drag-from-Select route. The implementation still requires explicit writing and preparation before dropping a new note or rest. It does not offer direct staff placement for every entry kind. The optional note-relative toolbar remains off by default pending native qualification. None of those facts establishes that the broader writing experience has passed native review.

The earlier **rest-semantics correction for selected-event deletion and blank-voice targeting** supplied the basis for this design. Deleting the last selected event in an ordinary voice leaves blank, incomplete musical work without synthesizing a rest. A rest is authored silence, not an editor placeholder. Emptying a pickup remains guarded because its span cannot be inferred from an empty voice: require an explicit musical decision or reject the operation without changing the score. Do not turn a pickup into a full bar, insert silent time, or infer a pickup length to make an operation succeed. At the proposal baseline, templates still started with rests and direct rest gestures were absent. The implemented empty starters and ordinary-rest gestures are the bounded changes listed above, not a migration of every creation route. Fixtures must continue to distinguish truly empty ordinary bars from existing full-measure rests.

The proposal baseline exposed several reasons that the app could feel less stable than its command model. The mode slot changed its visible action among Enter notes, Select, Resume, and Start bar; the active-mode button was hidden. Entry gave similar prominence to configuring a recipe, Insert, Drag, and Tools, while the staff-click path was mostly taught in help. A single note's Pitch chooser changed alteration, while letter and octave editing required another route. Rejection feedback could replace the selection actions needed to recover, and routine status could add height above the score. These historical source findings motivated the changes above; they are neither current defect claims nor measured usability results. The earlier copy finding, “Insert uses the current selection,” was also corrected during review.

Some apparent duplication is already avoided: entry and selection captions alternate, and Properties and Attached marks share a caption when their independently bound targets agree. Preserve those rules. Distinct draft owners must never be collapsed into a misleading common target.

The source basis is the [Author shell](../author.html), [workspace controller](../src/authoring/main.ts), [selection controls](../src/authoring/selection-controls.ts), [staff interaction](../src/authoring/staff-interaction.ts), and [layout styles](../src/authoring/author.css). This proposal supplements the [layout review record](author-layout-review.md) and [selection editing plan](author-selection-ui-plan.md); it does not turn their unverified native checks into passes.

The recommended responsibilities are:

| Surface | Main responsibility | What stays out of the ordinary writing path |
| --- | --- | --- |
| Score | Show authored music, the actual selection, and a temporary insertion preview or writing position | Form instructions, success paragraphs, setup controls, and permanent status overlays over notation |
| Compact music palette | Persistent Write notes / Select identity; current duration and relevant alteration or direction; a clearly owned next-note or selected-note context | Rare engraving policies, staff setup, exact source syntax, and several equally emphasized ways to submit the same note |
| One task pane | A deliberate event-detail, attached-mark, relationship, instruction, or measure task | A second competing inspector, automatic tab changes on passive selection, and automatic opening after each insertion |
| Document and Pages | Files, metadata, staves, parts, Source, page layout, and publication review | Routine pitch and rhythm entry |

Within the outer Write view, **Write notes and Select remain visible, distinctly named choices in fixed positions**, with the current choice indicated in text and accessible state, not color alone. The outer Write / Read / Pages navigation remains a workspace-view choice. Choosing the fixed **Write notes** control resumes a valid saved writing destination C with the unchanged recipe, even when B is selected. A nearby caption or accessible description names C; Resume is not an equal third mode or a replacement button in the mode slot. **Start writing here** is a separate, deliberate location action that establishes another destination. First entry uses the displayed initial writing point. If a previous bookmark becomes invalid, Write notes must not silently substitute B: explain the missing point and offer the local Start writing here task.

Reuse palette space, not musical state. In writing, its values belong to **New notes**. In selection, its accepted-value controls name **Selected …** or the exact selected set. Inspecting or correcting another event must not rewrite the insertion recipe. A dirty task pane names its retained owner; a different selection and a parked writing destination keep their own local identities. Ordinary menus retain intent; merely inspecting information or downloading a file does not park writing. Read and Pages suspend entry and remember the prior Write notes / Select intent. Returning to Write restores that intent and the valid bookmark; a missing bookmark remains visibly unresolved. Pending Source or invalid entry values continue to guard edits. Restoring intent never inserts music, applies Source, repairs a recipe, or writes history. Read and Pages still reject musical entry, and navigation that deliberately selects music must visibly enter Select rather than quietly retargeting writing.

For the common pitched-note task, the primary action is **choose a value, point at the staff, and place the note**. A visible preview explains pitch, onset, and voice before commitment. Exact keyboard entry remains equally capable. **Insert here** is a secondary, accessible alternative for the configured writing destination; it remains necessary for entry kinds without direct placement. Drag is another input method, not a second primary composition task. Dots and alteration should be available from the compact palette without requiring a long settings form. Exact pitch text, before/after/replace policy, and new-event engraving remain available through a small native options surface.

If a shortcut for dragging a new note while in Select is later retained, it must have an actual visible, explicitly named invoker such as **Drag new note**, with a separately reviewed rule for one-gesture entry intent and bookmark preservation. That is an optional proposal, not a current route. It must not be advertised merely because synthetic events can reach a hidden handle.

Selection should similarly make the common musical correction direct. A complete pitch route must be discoverable at every supported width; desktop accidental shortcuts must not hide access to the remaining spellings. Decide whether the label is Pitch, covering letter, octave, and alteration, or Spelling, explicitly describing its narrower scope. Do not advertise the latter as complete pitch editing. Chords remain whole events unless a separate chord-tone interaction is designed. Changing a written value must preserve unrelated properties and the insertion recipe. Keep explicit Apply boundaries for staged advanced tasks; do not make opening a palette commit pending form text.

Chord symbols and performance text deserve a direct creation action at a musical position, rather than living only among location-navigation commands. The first task can be a small HTML text field beside the notation with a clear commit and next-bar action. Recipients, exact fractional onset, and placement remain available when needed. Keep **attached to this event** distinct from **at this musical position**: moving a note must not silently move an independent instruction. Reuse the existing commands and draft guards; this proposal does not authorize editable SVG text or a new canvas-based score model.

Visual hierarchy should distinguish four things:

| Meaning | Proposed treatment |
| --- | --- |
| Paper and ink | A clearly bounded, calm score surface with dark notation; no interface tint masquerading as musical content |
| Application controls | Neutral chrome, readable labels, restrained borders, and one clear primary task at a time |
| Interaction | A limited accent for selection or insertion, also distinguished by outline, ghost notation, shape, or text; previews disappear on cancellation and never enter Source or print |
| Problems and pending work | Local warning/error treatment with a named recovery action; document-wide blockers appear once at workspace level |

The visual gate is observable: without reading help, a reviewer can identify the current mode, the primary next action, accepted ink, selected music, and a proposed mark. Use project targets of at least 4.5:1 contrast for ordinary text and 3:1 for large text and essential control/focus indicators against adjacent colors. Check visible focus, grayscale, and forced-colors presentation; selection and previews require distinguishable shapes or outlines as well as color. Semantic color and focus tokens must reach rendered SVG and overlays inside Shadow Roots, not just the outer stylesheet. Matching token names in CSS is insufficient if the actual overlay paint remains different. These are proposed checks, not completed native or accessibility certification.

Successful routine actions should not add a new row or recolor the page. A rejected correction should leave correction controls available, with its explanation adjacent and full details reachable through Review. Pending Source remains an explicit workspace-wide editing/publication blocker; it is not reduced to an optional hint. Retained form drafts remain visible without presenting several copies of the same warning. Keep one live announcement owner for each event.

The normal palette must have a **small, constant footprint**, with fixed mode, More, and common-control locations. Selection, feedback, and routine entry must not move these targets. Do not achieve stability by reserving the current large phone entry height in every state. Common choosers should overlay through native popovers; long tasks should be deliberate. More remains a true pane toggle with a fixed label and accurate expanded state. Explicit Edit mark, pitch-list, and keyboard Properties actions remain open actions, not accidental toggles.

For the prototype, target a **48px normal strip with controls at least 44px square**, at the default text size. Lock the slot map before application code changes. One candidate compact budget is 88px for the adjacent Write notes / Select controls, 144px for three fixed musical slots, 44px for More, 80px for Location, 12px for inter-group gaps, and 16px for outer padding: 384px in total. This is a layout hypothesis to measure at 390px, not evidence that labels or native controls already fit. Do not shrink targets or crop meaningful text to pass. Larger text or a narrower viewport needs an explicitly reviewed alternative layout.

Mode, More, and Location stay in their own fixed slots throughout the normal Write-view states. The desktop prototype can allocate a wider, fixed musical area with direct Flat / Natural / Sharp controls, retaining the compact complete-pitch route; this preserves the four-action correction gate. At 390px, the compact Pitch chooser accounts for the fifth action. Before implementation, the design review must lock the exact desktop slots and each event-family label, disabled state, keyboard order, and feedback location, and verify the compact budget with actual content. An eligible control must not shift sideways because a neighbor becomes unavailable.

Choose the **writing frame width independently of the task pane**, and preserve that frame and its system breaks when More opens or closes. Put a side pane only in genuinely spare width beside the chosen frame. If that space is unavailable, open the deliberate task sheet and return to the same writing frame and musical anchor. This does not require permanently reserving an inspector-width column. The tradeoff is simultaneous paper-and-form visibility versus line stability: preserve line stability and use a task view when both cannot fit. Do not shrink the notation, rewrap it on More, or overlay a long form on the music to claim both. Explicit viewport changes or a deliberate reading-width/refit choice are separate events that may establish a new frame.

On compact or very short screens, a deliberate **task sheet** can use the workbench area while preserving the score's position for Return to score. This is the same persistent HTML task pane, not a light-dismiss menu. Drafts and scroll survive, and returning restores the same writing frame, musical anchor, and a visible control. Do not promise that a full ensemble, long form, and software keyboard fit together. A small chooser remains a native popover; a long task has an explicit return path. In-flow disclosures are suitable inside such a form; they are not overlay menus. Any added select uses the existing customizable native-select enhancement and native fallback.

The current capability boundary is:

| Music to add | Current staff click / entry-handle drop | Current exact entry route | Important limit |
| --- | --- | --- | --- |
| Single pitched note, including supported quarter-tone spellings | Click in Write notes on a pitched staff; drop after Options → Prepare note drag | Insert here or Enter at the writing destination | Staff height chooses letter/octave; the recipe supplies alteration. No visible Select-mode entry-drag route is advertised. Preview and command validation still apply. |
| Chord | Not supported | Insert / Enter with the complete pitch list | A chord is one event; direct placement must not select or invent one of its tones. |
| Ordinary written rest | Click in Write notes on pitched, rhythm or three-roads staves; drop after Options → Prepare rest drag | Insert here / Enter with the ordinary Rest tool | Explicit duration and dots; vertical position has no pitch meaning. Respect the existing voice, event and tuplet boundaries. No automatic silence, splitting or padding. |
| Full-measure rest | Not supported | Insert here / Enter with an explicit full-measure-rest choice | Follows the measure rather than the ordinary-rest value. Empty space is not automatically a rest. |
| Single-line rhythm note | Not supported | Insert / Enter on a rhythm staff | Written rhythm without absolute pitch; vertical position cannot invent pitch. |
| Three-roads note | Not supported | Dedicated Direction chooser: Higher / Same / Lower, then Insert here / Enter on a three-roads staff | Direction refers to the previous main pitch in that voice, not an absolute pitch or interval distance. This does not imply road-note pointer entry. |
| Rhythmic slash | Not supported | Insert / Enter on an eligible pitched or rhythm staff | Prescribes attacks while leaving pitch unspecified; three-roads staves do not accept ordinary slashes. |
| Open slash | Not supported | Insert / Enter on an eligible pitched or rhythm staff | Rhythm remains improvised; nominal span is not a series of prescribed attacks. |

Existing eligible single-note pitch dragging is a separate correction operation, with fixed musical time and cancellation safeguards. It does not imply group dragging, chord-tone editing, or relocation of an existing rest. Ordinary-rest entry has its own bounded contract above. Ties, tuplets, annotations, attached modifiers, and supported engraving controls remain available through their existing dedicated tasks. Keep the documented Source boundaries; do not suggest every low-level attribute has a visual control.

The original decision compared three bounded alternatives:

| Alternative | Benefit | Cost and decision |
| --- | --- | --- |
| **Stable palette plus one task pane — chosen for implementation** | Predictable control locations, clear task ownership, strong keyboard/touch fallback, and a quieter paper surface | Requires simplifying the ordinary palette and making deliberate task transitions explicit. The implementation status above records progress without substituting for the acceptance gates. |
| Optional note-relative toolbar | Shorter travel from a selected note to a common correction | Can cover notation, move between systems, or lack room. Keep it optional and off by default until native clear-space, focus, touch, and fallback checks pass. It cannot be the sole route. |
| Gesture-only writing and editing | Minimal persistent chrome | Hides available actions, provides poor alternatives for unsupported event types and input needs, and makes mode/errors harder to explain. Rejected as the primary architecture. Gestures may supplement explicit controls. |

3. **Improve direct note entry and add explicit rest placement as a separate musical interaction change.** Build on the blank-voice correction's completed automated verification and use genuinely blank ordinary bars in the new first-use fixtures; native qualification remains a separate gate. Never manufacture intervening silence, split an existing event, choose a tuplet scope, or pad a bar merely to accept the drop. A full-measure rest remains a deliberate whole-voice action with its own eligibility rules. Keep release atomic and cancellation/invalid/stale gestures at zero writes. Chords, rhythm, roads, and slashes retain Insert / Enter until each receives a separately reviewed pointer contract. Any named drag-from-Select shortcut has its own visible-UI and intent tests.
4. **Review writing and performance continuity.** Run the task gates below against the prototype and integrated implementation. A failed gate gets a specific requirement, a failing regression where feasible, a bounded fix, and independent review. Test source/history invariants separately from native behavior. Do not count synthetic DOM geometry as native acceptance.
5. **Qualify supported native environments before approval.** With permission, verify real pointer/touch behavior, keyboard and screen-reader ownership, native select/popover behavior, software-keyboard layout, and actual score continuity.
